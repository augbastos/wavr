# Wavr site

The public Wavr website: what Wavr is, how it works, privacy, and how to get it running.
Static HTML/CSS/vanilla JS, no build step, no framework, no npm at runtime, zero external
requests (no CDN, no web fonts, no analytics). Same visual language as the product
dashboard (`frontend/index.html`).

**Status: built, never deployed.** No Cloudflare Pages project named `wavr-site` exists yet.
Nothing here has ever been pushed live. Publishing needs Augusto's explicit go-ahead — see
`CLAUDE.md`'s Canon PEAC rules on public/irreversible actions.

## Layout

```
site/
  wrangler.toml       # Cloudflare Pages config (pattern copied from infra/wavr-diag-worker)
  README.md           # this file
  public/             # the static output — this is what gets deployed
    index.html         # home: the transformation, Space, privacy, honest states
    how-it-works.html  # fusion mechanics, the five honest states, the surfaces
    download.html       # product-grade download page: Windows + Android, QR, advanced
    install.html        # every platform in full detail (macOS/Linux/Docker/source/Android/iOS)
    compatibility.html
    nodes.html
    privacy.html
    docs.html
    404.html
    assets/
      wavr.css              # one shared stylesheet
      wavr.js               # one shared script (platform detection + release lookup + QR)
      qrcode.vendor.js       # vendored qrcode-generator 2.0.4 (MIT), unmodified — see below
      releases.json          # download data, generated by scripts/gen_releases_manifest.py
      icon.svg               # self-hosted brand mark (copy of frontend/icon.svg)
      shots/                 # real product screenshots (see "Screenshots" below)
```

## Preview locally

For editing HTML/CSS/JS with no download buttons wired up:

```bash
cd site/public
python -m http.server 8080
# open http://127.0.0.1:8080
```

No build step. Editing any file and reloading is the whole workflow. On `localhost`,
`download.html`'s Windows/Android tiles correctly fall back to "not published here"
(there's no `/download/` route on a bare static server) and its QR code correctly
declines to render (`localhost` isn't reachable from a phone) — both are the intended
honest behavior, not a bug in this preview method.

To see real download buttons and a working "take this page to your phone" QR code, run
the actual portal instead (outside this agent's territory, documented here only because
it's how this site gets served for real — see `scripts/first_user_portal.py`):

```bash
python scripts/first_user_portal.py
```

That regenerates `releases.json` from `_local/first-user-rc/`, serves `site/public/` plus
`/download/<name>` on this machine's LAN address (never `127.0.0.1`), opens it in a
browser, and prints its own terminal QR code for first getting a phone onto the site —
independent of, and complementary to, the QR code `download.html` itself renders for
re-sharing that same page later.

## Deploy

**Do not run this without checking with Augusto first** — a Cloudflare Pages deploy is a
public, semi-irreversible action (Canon PEAC: public/irreversible needs explicit OK from
that conversation).

```bash
cd site
npx wrangler pages deploy public --project-name wavr-site
```

This creates the `wavr-site` Pages project on first run (project-scoped URL,
`https://wavr-site.pages.dev`, no account subdomain — same pattern as the existing
`wavr-diag` project). No custom domain is configured.

## `assets/releases.json` shape

Fetched same-origin by `install.html` and `download.html` at load, and by nothing else.
Generated by `scripts/gen_releases_manifest.py` (outside this directory — that script is
not this agent's territory; treat its output as read-only input here). Shape actually
shipped (schemaVersion 2):

```jsonc
{
  "schemaVersion": 2,
  "generatedAt": "2026-09-06T21:33:54Z",
  "generatedBy": "scripts/gen_releases_manifest.py",
  "sourceDir": "_local/first-user-rc",
  "note": "Local, unsigned first-user release candidate. Not signed, not on the Play Store, not for distribution beyond this test.",
  "products": [
    {
      "id": "windows-installer-exe",     // stable key the HTML's data-product="…" targets
      "product": "Wavr for Windows",     // shown as the download's title
      "platform": "windows",
      "maturity": "recommended",         // "recommended" | "specialized" | "experimental"
      "purpose": "One sentence, shown as-is under the title",
      "downloadName": "Wavr-Windows-Setup.exe", // shown next to the SHA-256, in a <details>
      "conflictsWith": ["some-other-product-id"],  // rendered as a "don't install alongside" note
      "available": true,                  // false or a truthy missingReason -> nothing rendered here
      "sizeBytes": 42551798,
      "sha256": "…",
      "modifiedAt": "2026-09-06T20:57:55Z",
      "downloadPath": "/download/Wavr-Windows-Setup.exe", // used verbatim as the button's href
      "outdated": false,
      "outdatedReason": null,
      "missingReason": null
    }
  ]
}
```

`wavr.js`'s `findProduct(releases, id)` looks a product up by `id`. Two HTML hooks consume
it: `<div class="release-slot" data-product="…" hidden>` renders a full download tile (used
for the primary product in a card), and `data-product-compact="…"` renders a single fallback
line (used for `windows-installer-msi`, the "installer not working? try this instead" case).
Either way, once a slot fills, the static `.no-release-note` paragraph in the same card is
hidden automatically, so the page never shows a live Download button next to text saying
nothing's been published.

Products present today (2026-09-06, the First User RC): `windows-installer-exe` (recommended),
`windows-installer-msi` (specialized fallback), `android-companion` (recommended — a real,
installable Android app, not just the browser-pairing route `install.html` also documents),
`android-core-brain` and `android-kiosk` (both experimental, gated behind Download's
"Advanced downloads" disclosure — the manifest's own `purpose` text already carries the
"do not install this today" / "replaces your home screen" warnings, which the HTML quotes
directly rather than re-inventing). No macOS/Linux products exist yet; those platforms fall
back to their static source-install instructions on `install.html` with no release-slot at
all. If a future product needs its own `data-product` hook, add one next to it rather than
reviving the old `data-os`/`DESKTOP_ARCHES` scheme, which this manifest shape replaced.

## Screenshots

`assets/shots/` holds real product screenshots, referenced with plain `<img class="product-shot">`
inside a `.shot-frame` wrapper. If a file listed below doesn't exist yet, the frame keeps its
reserved size and shows a calm placeholder (drawn in the product's own dashed "no coverage"
style) instead of a broken-image icon or a layout shift — see `wavr.js`'s image-error handler
and `.shot-frame--missing` in `wavr.css`. Expected files, all on the Home page today:

- `dashboard-overview.png` — the hero: the full room grid, occupancy + confidence per room.
- `room-states.png` — several room tiles side by side showing occupied / confirmed-empty /
  offline / no-coverage states distinctly, for the "Wavr says I don't know" section.

Neither is required for the site to work or to look intentional; add them (and reference any
further ones the same way) whenever they exist.

## Vendored: `assets/qrcode.vendor.js`

The npm package `qrcode-generator` v2.0.4 (`dist/qrcode.js`), copied byte-for-byte, MIT
licensed, copyright header preserved. Used only by `download.html`'s "take this page to your
phone" QR code (`window.qrcode(0, 'M')`, auto version, 15% error correction), entirely
client-side — no network request of its own, nothing sent anywhere. Round-trip verified
during development (encode → render → decode with `pyzbar`) for several representative URL
lengths; see `wavr.js`'s `renderPhoneQR()` for the loopback/`file:` guard that shows an
explanatory note instead of a QR code that couldn't actually be reached from a phone.

## Design notes

- Design tokens copied verbatim from `frontend/index.html:29-60` (dark-only,
  `--accent:#3db54a` reserved for confident/shipped state and primary actions, `--warn`
  for "needs attention / not published yet").
- `install.html` and `download.html`'s platform detection is feature-detected
  (`navigator.userAgentData.getHighEntropyValues`, falling back to `navigator.userAgent`
  parsing) and documented in full on `privacy.html`. It degrades to a fully usable, static
  "pick your platform" list with JavaScript disabled (progressive enhancement, not a
  requirement). `download.html` never hides either platform card based on the guess; it only
  adds a "detected for you" highlight.
- Every honesty gap that exists in the product today (the Node dashboard panel not built, the
  Android kiosk launcher unsigned and home-screen-replacing, the Android Core build with no
  first-run screen, macOS/Linux desktop-shell LAN HTTPS trust not implemented) is stated on
  the site rather than smoothed over, using the release manifest's own `purpose` text where
  one exists rather than re-writing it.
